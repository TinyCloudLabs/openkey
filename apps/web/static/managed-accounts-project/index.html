System model

OpenKey controls identity.
TinyCloud stores user data.

The tenant pre-provisions an email-bound signing account through OpenKey. The managed signer authorizes TinyCloud operations. PostgreSQL stores control-plane identity and custody state; it is not the document database.

Main product loop

Pre-provision first.
Associate when the user arrives.

Claim links and registration intents are gone. Email is the durable association point: the tenant may prepare data before signup, and verified OpenKey authentication later attaches that same account without merging it into the user’s personal key.

Tenant creates the account

POST /v1/accounts accepts a normalized email plus optional external ID and metadata. It returns the same account on an identical idempotent retry.

Tenant prepares TinyCloud data

The remote signer authorizes messages, typed data, digests, or unsigned transactions under fixed tenant-full-signing-v1 policy.

User verifies the same email

Email OTP or allowlisted verified Google identity binds every matching unowned account across organizations in one serializable operation.

OAuth returns the same key

A TENANT_MANAGED client discloses tenant control and includes only this organization’s managed key in its claims. The personal key remains separate.

User ejects permanently

A fresh passkey and exact custody epoch move the same address to terminal user custody. Every later tenant signing request rechecks custody and fails.

PostgreSQL stores

Control-plane truth

  • Identity: users, verified emails, passkeys, sessions
  • Tenancy: organizations, apps, OAuth clients, tokens
  • Custody: managed accounts, epochs, sealed keys
  • Operations: management credentials, idempotency, audit
TinyCloud stores

Application data

  • Documents: the Markdown file and other user content
  • KV data: tenant-prepared state authorized by signatures
  • Public proof: signer address and signature verification
  • Never: OpenKey private-key material or custody policy

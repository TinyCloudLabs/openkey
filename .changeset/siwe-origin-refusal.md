OpenKey refuses to sign a SIWE (EIP-4361) message that does not name the site asking for it (TC-1486). A message is SIWE-shaped when it has the `… wants you to sign in with your Ethereum account:` header, or both `URI:` and `Nonce:` lines; the check also covers SIWE text hidden in a `0x…` hex message. Its `domain` must equal the verified requesting origin's host (with port) and a web `URI:` must have exactly that origin; a `did:key` URI (TinyCloud session delegation) is bound by its domain. Differences in case are normalised; whitespace, userinfo, a trailing dot, punycode or unicode lookalikes, a different scheme or port, and a second mismatching header or URI are refused. An unattributed origin (`*`, missing, malformed) is refused. There is no user override.

`/widget/sign` and `/widget/embed/sign` show a refusal instead of the approval screen and reply `UNKNOWN` with a `SIWE_ORIGIN_REFUSED: <reason>` message. The server enforces the same rule: `POST /api/keys/:keyId/sign` and `POST /api/delegate/authorize-sign-prepare` take a `requestOrigin` (the postMessage sender the widget verified) and return `403 siwe_origin_refused` with a `reason` (`unattributed-origin`, `invalid-origin`, `incomplete-siwe`, `domain-mismatch`, `uri-mismatch`) before any key is unsealed or context issued. Loopback origins (`localhost`, `127.0.0.1`, `[::1]`) also accept the bare hostname, because `@tinycloud/web-sdk` emits `location.hostname` without the port. Non-SIWE messages are unchanged. Prepared-handoff (CLI) requests carrying a ticket are exempt: their requester is a local CLI, not a browser origin.

What breaks: a SIWE sent without `requestOrigin` to `/api/keys/:keyId/sign` (including one typed into the dashboard key page), and a SIWE signed through the legacy unattributed `*` widget path, now get refused. Callers whose SIWE `domain` is not the page's host (for example a pinned domain served from another host) are refused until their domain is fixed.

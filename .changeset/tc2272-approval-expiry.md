The approval screen shows "Approval expires: 7d (Change)", defaulting to the expiry the app requested. Change opens a picker (1 hr, 24 hr, 7d, 30d) and a box that takes a time like 5600s, 90m, 40d or 1y (units s, m, h, d, w, y; a year is 365 days). A time over one year shows "That's a long time. OpenKey can't cancel it early once you approve." The time the user picks is what OpenKey signs as the message's `Expiration Time`. Where it shows and what can be picked: an app sign-in in the popup or frame, only when the app's request carries `expiryChangeable: true` (current SDKs reject a changed expiry), any time, through `/api/delegate/authorize-sign-preview` (new optional `expirationTime`, an exact ISO-8601 UTC time after now and after the request's Issued At) sealed in the preview approval and signed by `/authorize-sign` exactly as previewed; the prepared CLI handoff, up to what the CLI asked for (it refuses a longer grant), the same way; a signed CLI approval request and a device approval, up to what the requester signed (`assertDelegationWindow` now allows a shorter grant, never a longer one); the plain `/delegate` link, any time (a new `expiryChosen: true` on `/prepare` and `/api/delegate` skips the 30-day clamp that still applies to a link's own `expiry`). The exact-byte path for requests without a protocol version shows no control. Details: TC-2272

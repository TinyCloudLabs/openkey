`/api/delegate/authorize-sign-preview` and `/api/delegate/authorize-sign` check the exact bytes they are about to return or sign against the request the app made at `/authorize-sign-prepare` and the owner's selection, and refuse with `400 signed_exceeds_request` and a `reason` naming the first difference. Both messages must parse under a strict EIP-4361 and EIP-5573 reader that re-serializes them byte for byte (repeated, unknown or out-of-order fields, repeated resources or JSON keys, a second ReCap, padded or non-canonical base64url are refused). The signed message must keep the requested domain and scheme, address, URI, version, chain id, nonce, issued-at, not-before and request id; keep every non-ReCap resource; keep the requested statement with only its ReCap sentence rewritten for the signed capabilities; carry only requested (resource, ability) pairs with their requested caveats, only requested proofs, and only capabilities the owner left selected. The expiration must equal the requested one unless the owner picked another at preview; a later picked time still needs the app's `expiryChangeable: true` and is never available to a CLI handoff.

What can now be refused that was signed before: any request the strict reader refuses (for example one ending in a line feed or using CRLF), narrowing a request whose statement carries text before the ReCap sentence (the regenerated message dropped that text), narrowing a request whose statement is not the ReCap sentence the WASM writes (for example a hand-written statement), and narrowing a request that lists another resource before its ReCap (the regenerated message moved the ReCap first). Requests produced by `prepareSession` are unaffected. Details: TC-2198

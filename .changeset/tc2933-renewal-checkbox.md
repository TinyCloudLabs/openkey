The approval screen's "Approval expires: 30d (Change)" line is replaced (TC-2933).

- Where the requester signed a renewal request (`renewal: { version: 1, leaseLifetimeSeconds }` on a signed approval request), the line is one checkbox: ticked, "This permission renews automatically for up to 90 days"; unticked, "This permission expires in 30 days", with the real lengths filled in. It starts ticked only when the request's signed `purpose` is `standing` and nothing in it reaches secrets or decrypt; a task, or a request with no purpose, starts unticked. Ticking it on a request that reaches secrets or decrypt first asks "Renew sensitive access?", and turning renewal on there uses a 7-day window.
- Where the box shows, the app-key "This access lasts until <date>." line is no longer shown beside it (a fixed end date is wrong while renewal is on, and repeats the line while it is off); it is unchanged elsewhere.
- Everywhere else the line reads "This permission expires in <window>", with no box.
- How long the permission lasts, and how long renewal can go on (90 days, 6 months, 1 year or a typed time, never more than the request signed or one year), are changed under a closed "How long it lasts" fold. There is no "(Change)" link.
- The choice is part of the preview: `/api/delegate/prepare` takes `renewal: { choice: "leased", leaseLifetimeSeconds }` or `{ choice: "finite" }` and binds it into the authorization context, and ticking, unticking or changing the lease prepares a new preview. Approving uses only the bound choice; an approve body may repeat it, and any other `renewal` in it is refused with 400 before anything is signed. After the grant is signed and registered with its node, OpenKey signs, as the owner, a lease whose only ability is `tinycloud.delegation/renew` on `urn:cid:<the grant's CID>`.
  - The lease's audience is the renewer the grant's own node advertises at `/.well-known/tinycloud/node-keys` (checked against the node's `/info` id; only known TinyCloud nodes, no redirects, a 5-second timeout and a 16 KiB answer cap). On the production node its DID must equal `OPENKEY_RENEWAL_NODE_DID`, and without that setting no production lease is made. The lease ends at approval time plus the chosen lease.
  - The node admits it, and the encrypted approval result gains `renewalChoice` (`leased` or `finite`) and, when leased, `renewal: { version, approvedLeaseLifetimeSeconds, approvedAt, receipt }`, checked with the codec's `parseApprovalRenewal` before it is encrypted.
  - Each step is saved on the approval request (new nullable `renewal` column). A signed lease is collected by a retry only for the same owner and length; a finite or different choice gets 409 `renewal_already_signed`. An unsigned step is rebuilt from the current approval. The saved steps are cleared when the request is approved, denied or its result acknowledged, and from requests that expired without a result. If the lease can't be set up, nothing is approved: "OpenKey couldn't set up renewal. Nothing was approved. Try again."
- An external wallet signs the lease as a second signature: `POST /api/delegate/complete` answers `{ renewalSignature: { message, leaseLifetimeSeconds } }` instead of saving, the screen shows "Sign once more to turn on renewal for up to <lease>", and the wallet's signature goes to the new `POST /api/approval-requests/:id/renewal-signature`, which checks it recovers to the grant's owner. Declining it approves nothing.
- Leases are off unless `OPENKEY_RENEWAL_LEASES=enabled`. `/api/approval-requests/:id/load` reports it as `renewalAvailable`; while it is off a renewal request shows the plain expiry line and is approved finite, and a leased choice is refused.
- The API's `@tinycloud/node-sdk` and `@tinycloud/sdk-core` move from 2.11.0 to 3.12.0-beta.22, `@tinycloud/node-sdk-wasm` from 1.7.6 to 1.7.9-beta.0, and `@tinycloud/share-envelope` from 1.4.1-beta.1 to 1.6.0-beta.1.

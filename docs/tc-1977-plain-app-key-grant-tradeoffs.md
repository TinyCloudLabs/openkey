# Plain browser app-key grants: contract and tradeoffs

**Decided 2026-10-31: optional manifest (Sam).** PR #384. The question was whether browser app-key grants need a published, digest-bound OpenKey manifest, or whether a verified browser origin and ordinary user approval are sufficient. Sam chose the optional manifest. The rest of this document is the record of the options. Builder-facing behavior is in [App keys for builders](app-keys-for-builders.md).

## Two different bindings

The browser channel supplies `requestOrigin`, which the server checks against the SIWE domain and URI before it prepares a browser sign-in. For app keys, the origin must additionally be HTTPS, a host that can name an app, and byte-for-byte equal to the origin used in admission. This is the browser/channel and SIWE binding; it does **not** fetch a file.

Separately, `/authorize-sign-prepare` may fetch `https://<reportedOrigin>/.well-known/openkey-manifest.json` when the display presentation includes a nonempty `manifestDigest` and the reported origin is HTTPS. The server canonicalizes the fetched JSON and compares its SHA-256 with that digest. A match labels the metadata `origin-bound` and supplies manifest declarations; absent digest means no fetch. The fetch is an extra network dependency, not what proves which browser origin sent the request.

## Current `main` versus the PR #384 proposal

On current `main`, an ordinary browser sign-in with no `apps/` key resources follows the normal capability-review/default-selection path and is not gated on an app manifest. The user still sees and approves the requested default-selected capabilities; this is not automatic consent. A browser SIWE that includes app-key resources takes a separate app-key admission path and, when its browser/report origins are valid but no digest-matched manifest supplied declarations, is refused with `manifest_unverified`. Invalid or missing origin inputs can be refused earlier as an origin error. This baseline is visible in [current `main` at `delegate.ts` lines 2664–2682](https://github.com/TinyCloudLabs/openkey/blob/aae189284406b2f4e520ebca816a242ca7544b16/apps/api/src/routes/delegate.ts#L2664-L2682), where admission receives only `metadataTrust.status === 'origin-bound'` and bound manifest declarations, and [`app-key-gate.ts` lines 224–232](https://github.com/TinyCloudLabs/openkey/blob/aae189284406b2f4e520ebca816a242ca7544b16/apps/api/src/services/app-key-gate.ts#L224-L232), which returns `manifest_unverified` when that flag is false. The route only enters this branch for app-key candidates; ordinary sign-ins without `apps/` resources are unaffected.

PR #384 changes only that app-key-specific admission branch: when a bound manifest is unavailable, derive a fixed app namespace from the verified browser origin and admit eligible requests under that prefix and the fixed ability set below. The ordinary non-app-key sign-in/default-delegation flow remains unchanged. Admitted app-key actions then enter the same explicit review and approval process.

| Case | App-key admission and scope | Metadata and review UI |
| --- | --- | --- |
| Ordinary browser sign-in, with no app-key resources (current `main` and PR proposal) | Normal requested-capability preparation; no app-key admission check is entered. | Existing default selection and user review continue. Missing manifest metadata stays unsigned; it does not block ordinary sign-in. |
| App-key SIWE on current `main`, without a digest-matched manifest | Refused as `manifest_unverified`; there are no app-key rows to approve. | The app-key request does not reach the approval UI. |
| App-key request with a digest-matched manifest (current `main` and PR proposal) | Require the manifest app ID to bind to the browser host and each requested resource and ability to be declared in its `keys` block. The server does not rewrite the request to narrow it: an undeclared path/ability refuses the app-key grant. | Origin-bound manifest name/ID may be shown as such. Declared secret/permission metadata can classify matching grants; it never expands the requested ReCap authority. |
| App-key SIWE without a digest-matched manifest (PR #384 proposal) | Derive the app namespace from the verified browser origin's reversed host and synthesize one `apps/<origin-app-id>/` prefix permitting `key.create`, `decrypt`, `key.block`, and `key.unblock`. | Metadata stays unsigned. Caller-provided names remain visibly unverified; the resource app ID and verified origin identify the request. Only abilities present in the request become rows. |

For example, `https://listen.tinycloud.xyz` derives app ID `xyz.tinycloud.listen` and key namespace `apps/xyz.tinycloud.listen/`. The prefix may request `key.create`, `decrypt`, `key.block`, and `key.unblock`; the app-key request must still include a valid SIWE `Expiration Time`.

Admission in both app-key cases still requires a browser request (no handoff ticket), checked SIWE origin, own signer DID and `default` network, declared path/ability, and a valid SIWE `Expiration Time`. `key.delete` remains refused. The requested SIWE expiry bounds the access; this change adds no separate app-key lifetime ceiling. The PR does not inject capabilities into the SIWE: it admits or refuses the caller's requested paths/abilities. In the review model, requested actions start selected by default; the user must still approve, and app-key actions are grouped so they can keep the group or remove it. `key.delete` is shown as non-approvable. Decrypt is marked sensitive. So this change can make a previously refused app-key request part of the default selected review, even though it does not silently change unrelated capability grants. See [`parse.ts` lines 652–705](https://github.com/TinyCloudLabs/openkey/blob/53538faf4e8d01add555bd2d7710724a6408cfa5/packages/capability-review/src/parse.ts#L652-L705) and [`restrict.ts` lines 52–62](https://github.com/TinyCloudLabs/openkey/blob/53538faf4e8d01add555bd2d7710724a6408cfa5/packages/capability-review/src/restrict.ts#L52-L62).

### Manifest outcome branches in the current code

- **No digest:** no fetch is attempted; metadata is unsigned. With PR #384, when `reportedOrigin` is absent the route supplies `requestOrigin` to admission and can use the synthesized origin prefix. If a caller supplies a nonmatching or invalid `reportedOrigin`, admission refuses it rather than silently replacing it.
- **Digest present but no HTTPS `reportedOrigin`:** no fetch is attempted and metadata is unsigned. The same exact-origin rule applies: admission succeeds only if the origin value passed to the gate is valid and matches the verified browser `requestOrigin`.
- **Fetch, JSON, digest, DNS, timeout, size, or other bind failure:** metadata is downgraded to unsigned. With PR #384, admission then follows the same origin-derived fallback, provided the browser-origin/account/network/expiry constraints pass. The test suite covers digest-mismatch/unfetchable and no-digest branches; it does not exercise every network or malformed-body failure end to end.
- **Digest matches, but the fetched manifest has no `keys` block or an empty one:** the manifest is origin-bound, but the app-key request is refused because it declares no usable key entries.
- **Digest matches and `keys` is malformed (including invalid `keys_app_id`):** the manifest is origin-bound, but admission refuses the app-key request as unreadable. Invalid UTF-8, malformed JSON, a non-object JSON value, or digest mismatch fails the bind before declarations are extracted and therefore follows the unsigned fallback above.
- **Digest matches and declarations are valid:** only declared paths/prefixes and the declared supported abilities can pass; a mismatched app host, owner, network, ability, or missing/unparseable expiry is refused.

## Options and recommendation

| Option | Builder/user benefit | Cost and authority effect |
| --- | --- | --- |
| **Domain-bound only** | No manifest file, digest generation, or server fetch. A normal browser sign-in can request app keys immediately. | Every qualifying app origin gets the fixed origin prefix and four supported abilities; the developer cannot narrow that scope through a declaration. Users must inspect and approve the requested rows. Metadata stays unsigned. |
| **Optional manifest metadata** | Plain sign-in works without setup; builders that publish a manifest get a verified label and can declare narrower key prefixes/abilities. | A digest-bearing request adds a fetch and can fail. Under the current PR, failure/absence falls back to the broader origin prefix, while a valid manifest can narrow it. This asymmetry must be explicit to builders and users. |
| **Required well-known manifest** | Every app-key request has an origin-fetched, digest-matched declaration; the manifest can enforce least privilege and provide origin-bound metadata. | Builders must publish and keep the file/digest available and correct. DNS/TLS/HTTP availability, timeout, size, and parsing become sign-in dependencies; no usable manifest means the app-key grant is refused (ordinary non-app-key sign-in remains separate). |

**Code-grounded recommendation (adopted):** if the product requirement is that plain browser sign-in work without manifest setup, choose **optional manifest metadata**: it preserves the existing honest provenance UI and its manifest-based narrowing when the bind succeeds, while keeping ordinary origin-derived approval available. A valid manifest narrows the request, but missing or failed verification does not; those cases permit the fixed origin prefix and four abilities, still subject to the user's review and the account/network/expiry rules above. The required-manifest option was the safer alternative and was not chosen.

## Evidence and proof boundary

The behavior change is the `/authorize-sign-prepare` admission block in `apps/api/src/routes/delegate.ts`, with origin-derived app IDs in `appIdForOrigin` and the admission rules in `apps/api/src/services/app-key-gate.ts`. `apps/api/src/__tests__/app-key-admission-routes.test.ts` covers manifest-free prepare → preview → explicit `/authorize-sign`, the refusals (other prefixes, other owner or network, `key.delete`, mismatched origins), and a bound manifest still narrowing the request. A local end-to-end browser sign-in with no manifest was also run (2026-10-31): the consent screen showed the app-key rows and the signed message carried the four abilities.

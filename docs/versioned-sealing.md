# Versioned sealing and re-seal maintenance

## Compatibility and configuration

Production continues writing generation (`kid`) 0 in the existing headerless
format. Its derivation paths and key bytes are unchanged. The previous release
can therefore read every blob newly written by this release. This deliberately
retains the legacy format's lack of record-binding AAD until a later write
generation is explicitly configured. Existing headerless rows are generation 0;
there is no attempt to infer another provider after a failed decrypt.

`SealingKeyring` takes `{ providers: ReadonlyMap<number, SealingKeyProvider>,
writeKid?: number }`. `writeKid` defaults to 0. A provider asynchronously returns
the sealing key for `(resolvedSealingContext, kid)`; production registers only
provider 0 through the existing `TeeClient.deriveKey` implementation. Other
providers must be supplied explicitly by the embedding process. No environment
variable selects a generation. Unknown generations fail closed with a fixed
message. Deterministic providers for generations 0 and 1 exist only in tests.

`seal(plaintext, binding)` and `unseal(blob, binding)` accept
`{ recordId, sealingContext }`. Here `sealingContext` is the **resolved derivation
path**: `openkey/key/<opaque-context>` or, for a legacy row whose context is null,
`openkey/user/<user-id>/keys`. Empty or malformed non-null contexts never fall
back to the legacy path. The API's default write helper preserves headerless
writes, while all custody reads recognize the versioned format.

## Bytes and authentication

All blobs are standard base64. Decoded legacy generation 0 bytes are unchanged:

```
iv[12] || authenticationTag[16] || ciphertext
```

An explicitly selected nonzero generation writes:

```
header[13] || iv[12] || authenticationTag[16] || ciphertext
header = ASCII("OKSEAL\r\n")[8] || formatVersion:u8(1) || kid:u32BE
```

The primitive remains AES-256-GCM with a fresh cryptographically random 12-byte
IV and a 16-byte tag. The versioned format authenticates these exact AAD bytes:

```
header[13]
  || recordIdUtf8ByteLength:u32BE || UTF8(recordId)
  || contextUtf8ByteLength:u32BE  || UTF8(resolvedSealingContext)
```

Lengths count UTF-8 bytes, not characters. Length prefixes prevent ambiguous
concatenation; the full header binds the generation and format. Changing a
record ID, context, or generation fails authentication even if providers return
the same key bytes. A recognized header with an unsupported version or truncated
body is rejected, never retried as legacy. Headered generation-0 input is
rejected: generation 0 has exactly one format, the original headerless format.
A random legacy IV could theoretically collide with the 8-byte magic; such a
row fails closed rather than attempting an unauthenticated downgrade.

The fixed headerless fixture was generated by the pre-change `seal` primitive
with deterministic TEST inputs before adding the keyring. It remains readable by
both the unchanged primitive and the keyring. The existing derivation
known-answer test and derivation implementation are unchanged.

## Offline maintenance

`runKeyReseal` accepts a keyring, repository, and `KeyResealCursorStore`.
`PrismaKeyResealRepository` operates on managed Ethereum rows with sealed data
and all Nostr rows, including archived/revoked rows. Each table is paged by
`ORDER BY id ASC`, with `id > lastId`. Legacy user-path rows use their existing
path. There is no schema migration, HTTP route, timer, or automatic invocation.

The library defaults to `dryRun: true`: verification-only, no sealing, no
compare-and-swap, no row updates, and no cursor reads or writes. It scans both
tables from the beginning regardless of an existing checkpoint. Current rows
are verified and counted; `resealed` remains 0, and a nonzero remaining count
is a normal dry-run result. Library callers must explicitly pass `dryRun: false`
to apply writes. Only apply mode uses/resumes persistent checkpoints.

The cursor records the target generation, table, last verified ID, cumulative
counts, and completion marker. `FileKeyResealCursorStore` requires an explicit
absolute path on a durable volume, writes a private temporary file, fsyncs it,
atomically renames it, and fsyncs the directory. Run one maintenance owner per
cursor path. A different target cannot resume an incomplete cursor. Completed
cursors start a fresh verified pass on the next invocation. Losing the cursor
may repeat verification, but does not double-seal current rows.

In apply mode, for each row the job:

1. Opens the row using its header's provider (headerless means 0).
2. Derives and compares the Ethereum address or Nostr public key to the stored
   identity. Current-generation rows are verified before being skipped.
3. Re-seals under `writeKid` and compares-and-swaps the old blob, ID, context,
   user, and identity. A lost CAS is counted and retried after a fresh read,
   with a bounded retry limit; exhausted retries stop without advancing.
4. Reads the committed row from the repository, opens the persisted new blob,
   and verifies its identity and generation again before checkpointing.

A crash after a committed write but before checkpointing replays the row and
verifies/skips the current generation. Any verification failure stops the pass
immediately, with no later-row writes. Failure output is sanitized; it never
contains a row ID, exception diagnostic, plaintext, derived key, or blob.
Only `scanned`, `alreadyCurrent`, `resealed`, `raced`, `failed`, and
`remainingOldGeneration` counts and a `dryRun` boolean mode label are
returned/emitted. A failed result means the pass is not verified, irrespective
of its remaining count. A successful dry run does not certify completion of
an apply pass.

`remaining(oldKid)` performs an independent keyset scan of both tables and
counts actual stored generations, not this pass's updates. In apply mode,
remaining old rows force a fresh pass and a failed result when the target
differs. Providers must remain registered while their data may still be read.
A final count is not a lock against concurrent inserts.

For later explicitly configured maintenance, the order is mandatory:

1. Switch every application writer to the chosen nonzero generation before
   starting the job. Production intentionally still writes 0 in this release;
   this release alone is not a configuration for running later maintenance.
2. Keep both providers available while the job completes a full verified pass
   reporting `failed = 0` and `remainingOldGeneration = 0`.
3. Remove the old generation's reader/provider only after that verified pass
   and confirmation that no writer can produce it. For generation 0 this
   requires removing **both** provider-map entry 0 **and** the separate
   headerless legacy-reader branch in
   `apps/api/src/services/key-sealing.ts` (`unsealKeyForRecord`, currently
   lines 74-75). Removing only the provider is insufficient because that
   branch calls the legacy primitive directly. Removing both prevents an
   old-format blob being substituted after the transition. The previous
   release is no longer a valid rollback target once nonzero writes begin.

Signing does not cache unsealed keys between requests. Each request fetches a
record and opens it for its operation; maintenance never modifies the plaintext
identity. Consent/renewal paths that pre-open before acquiring a transaction
lock compare key ID and address. If the blob or derivation metadata drifted,
they discard the pre-opened plaintext, release locks, re-read/open the current
row, and revalidate the whole transaction before signing (one bounded retry).
Background onboarding retries fetch the current sealed row rather than retain
an old blob or plaintext across waits.

## Entry point

`runResealKeys(config)` is callable inside the API/TEE process and defaults to a
read-only dry run. Applying requires `runResealKeys(config, { apply: true })`.
The CLI commands are:

```
bun run scripts/reseal-keys.ts /absolute/path/to/config.ts
bun run scripts/reseal-keys.ts /absolute/path/to/config.ts --apply
```

The first command is verification-only; only the second may write rows or a
checkpoint. Unknown flags fail closed. Configuration cannot implicitly opt in
to apply mode. That operator-owned module exports `resealConfig` with an
explicitly constructed keyring, repository, durable `cursorPath`, and optional
batch/retry/count-query settings. There are no implicit database or provider
defaults. The CLI emits only six numeric counts and the `dryRun` mode label,
and exits nonzero on failure. This change does not run maintenance or supply a
production configuration for a later generation.
